# Техническое задание
## Spring Boot MVC-приложение: преобразование OpenSearch Query DSL в ClickHouse SQL

**Версия:** 1.0  
**Дата:** 11 ноября 2026 г.  
**Статус:** проектное ТЗ для MVP. Требования отражают предварительные решения разработчика; перед расширением функциональности их следует согласовать с руководителем.

---

## 1. Назначение документа

Документ определяет требования к минимальному Spring Boot MVC-приложению, которое принимает ограниченный поднабор OpenSearch Query DSL и преобразует его в параметризованный SQL для ClickHouse.

Приложение на первом этапе **только генерирует SQL**. Оно не подключается к OpenSearch или ClickHouse, не выполняет запросы и не хранит логи.

## 2. Контекст и цель

В OpenSearch и ClickHouse предполагается хранить одинаковые события журналирования. Для каждого типа источника могут использоваться отдельные индекс OpenSearch и таблица ClickHouse: например, `windows_logs`, `linux_logs`, `network_logs`.

У разных типов логов есть общие поля (`timestamp`, `source`, `message`) и специфичные поля (`EventID`, `process_name`, `protocol` и т. п.).

**Цель MVP:** реализовать архитектурно изолированный и тестируемый компонент, преобразующий поддерживаемую часть OpenSearch Query DSL в SQL ClickHouse с безопасной передачей значений через параметры.

## 3. Границы MVP

### 3.1 Входит в MVP

- Spring Boot MVC-приложение без frontend.
- REST endpoint для преобразования запроса.
- Swagger UI / OpenAPI для ручной проверки.
- Входной JSON с именем таблицы и объектом `query`.
- Проверка имени таблицы и полей по YAML-конфигурации.
- Разбор поддерживаемого поднабора DSL в промежуточное AST.
- Генерация SQL ClickHouse и отдельного упорядоченного списка параметров.
- Структурированные ошибки и корректные HTTP-коды.
- Unit-тесты парсера, валидаторов и SQL-генератора.

### 3.2 Не входит в MVP

- Подключение к OpenSearch и ClickHouse.
- Выполнение сгенерированного SQL.
- Авторизация, аутентификация и пользовательский интерфейс.
- Агрегации, сортировка, пагинация, `size`, `from`, `_source` и полный Search API body.
- Поддержка всего OpenSearch Query DSL.
- Автоматическое получение схемы таблиц из ClickHouse.
- Сравнение результатов двух баз в интеграционных тестах (это последующий этап).

## 4. Термины

- **OpenSearch Query DSL** — JSON-формат описания поискового запроса OpenSearch.
- **AST (Abstract Syntax Tree)** — внутреннее дерево условий запроса, не зависящее от JSON и SQL.
- **SQL Generator** — компонент, преобразующий AST в SQL и параметры.
- **Allowlist** — явно заданный список разрешённых таблиц и полей.
- **Параметризованный SQL** — SQL, в котором значения передаются отдельно от текста запроса через placeholders.

## 6. REST API

### 6.1 Endpoint

`POST /api/v1/query/translate`

Назначение: преобразовать `query` для указанной таблицы ClickHouse в SQL.

### 6.2 Формат запроса

```json
{
  "table": "windows_logs",
  "query": {
    "term": {
      "source": "192.168.1.10"
    }
  }
}
```

`table` — поле собственного API, не часть OpenSearch Query DSL.  
`query` — объект OpenSearch Query DSL. Не принимать полный Search API body вместо `query`.

### 6.3 Успешный ответ

```json
{
  "sql": "SELECT * FROM windows_logs WHERE source = ?",
  "parameters": [
    "192.168.1.10"
  ]
}
```

SQL и параметры должны формироваться в одном проходе и сохранять строгий порядок соответствия placeholders и значений.

### 6.4 Общие правила API

- JSON должен иметь `Content-Type: application/json`.
- Пустые или отсутствующие обязательные поля отклоняются.
- Неизвестные свойства верхнего уровня: поведение определить явно в DTO/Jackson-конфигурации; предпочтительно отклонять, чтобы опечатки не оставались незамеченными.
- Не возвращать stack trace, внутренние пути файлов, SQL-конфигурацию или секреты.
- Не включать значения пользовательских данных в диагностические сообщения без необходимости.

## 7. Разрешённые таблицы и поля

### 7.1 Конфигурация

Список таблиц и полей задаётся в YAML, например:

```yaml
query-translator:
  tables:
    windows_logs:
      fields:
        - timestamp
        - source
        - message
        - EventID
    linux_logs:
      fields:
        - timestamp
        - source
        - message
        - process_name
    network_logs:
      fields:
        - timestamp
        - source
        - message
        - protocol
```

Фактический префикс и способ binding в `@ConfigurationProperties` выбрать единообразно.

### 7.2 Требования безопасности

- Имена таблиц и полей нельзя передавать как обычные SQL bind-параметры.
- До генерации SQL проверить, что таблица присутствует в allowlist.
- Каждое поле из DSL проверить по allowlist именно выбранной таблицы.
- В SQL включать только проверенные идентификаторы.
- Нельзя считать экранирование произвольного имени достаточной заменой allowlist.
- Не строить имя таблицы/поля конкатенацией из непроверенного пользовательского ввода.

### 7.3 Типы полей

Для MVP требуется определить типы значений для `range` и поведение сравнения. Минимальная безопасная рекомендация — расширить YAML-описание полей типом (`STRING`, `NUMBER`, `TIMESTAMP`, `BOOLEAN`) до реализации `range`, если тип нельзя надёжно вывести из значения. Не выполнять неявное и неоднозначное преобразование типов.

Пример расширенной конфигурации (предлагаемый формат, не окончательно согласованное требование):

```yaml
query-translator:
  tables:
    windows_logs:
      fields:
        timestamp: TIMESTAMP
        source: STRING
        message: STRING
        EventID: NUMBER
```

Если для MVP выбран простой список строк, парсер обязан валидировать допустимые формы значений и возвращать понятную ошибку при неоднозначности. Предпочтительно согласовать типизированную конфигурацию до реализации `range`.

## 8. Поддерживаемая часть OpenSearch Query DSL

Поддержка ограничена перечисленными конструкциями. Не заявлять совместимость со всем DSL.

### 8.1 `term`

Точное сравнение поля со значением.

Пример:

```json
{"term":{"source":"192.168.1.10"}}
```

Ожидаемая форма SQL:

```sql
source = ?
```

Для строковых полей требуется проверить различия между OpenSearch mapping/analyzer и типом ClickHouse. Равенство в SQL не всегда эквивалентно поведению `keyword`, `text` и анализаторов OpenSearch.

### 8.2 `terms`

Сравнение со списком допустимых значений (семантика «любое из значений»).

```json
{"terms":{"EventID":[4624,4625]}}
```

Ожидаемая форма:

```sql
EventID IN (?, ?)
```

Пустой массив должен обрабатываться явно и детерминированно (предпочтительно отклонять как некорректный/неподдерживаемый ввод, а не генерировать сомнительную конструкцию `IN ()`).

### 8.3 `range`

Поддержать границы `gt`, `gte`, `lt`, `lte` и объединять заданные границы через AND.

```json
{"range":{"timestamp":{"gte":"2026-11-01T00:00:00Z","lt":"2026-11-02T00:00:00Z"}}}
```

SQL-форма:

```sql
timestamp >= ? AND timestamp < ?
```

Нужно валидировать, что:
- задано хотя бы одно допустимое условие;
- не переданы конфликтующие/повторные границы;
- тип значения соответствует типу поля;
- формат даты/времени определён и тестируется;
- неподдерживаемые параметры `range` (например, `format`, `time_zone`, `relation`) не игнорируются молча.

### 8.4 `exists`

Проверка существования поля.

```json
{"exists":{"field":"message"}}
```

Для обычного столбца SQL-форма может быть `message IS NOT NULL`, но это **не гарантирует** эквивалентность OpenSearch `exists` во всех моделях данных. Для JSON/Object/Map, Nullable, пустых строк и отсутствующих ключей семантика зависит от схемы ClickHouse и способа хранения.

В MVP определить поддерживаемую модель: рекомендуется считать поля отдельными колонками ClickHouse и документировать, что `exists` означает SQL `IS NOT NULL` для Nullable-колонки либо эквивалентную проверку для не-Nullable колонки. Если модель таблиц не определена, не заявлять полную семантическую совместимость.

### 8.5 `bool`

Поддержать:
- `must` — логическое AND;
- `should` — логическое OR в чётко оговорённой области;
- `must_not` — логическое NOT.

Пример:

```json
{
  "bool": {
    "must": [
      {"term":{"source":"192.168.1.10"}},
      {"range":{"EventID":{"gte":4000,"lte":5000}}}
    ],
    "must_not": [
      {"term":{"message":"debug"}}
    ]
  }
}
```

Ожидаемая логическая форма:

```sql
(source = ? AND EventID >= ? AND EventID <= ? AND NOT (message = ?))
```

**Семантические ограничения `bool`:**
- В OpenSearch `should` не всегда означает обязательный OR-фильтр: значение `minimum_should_match` зависит от наличия `must`/`filter` и явной настройки.
- В MVP либо реализовать документированную ограниченную семантику, либо отклонять комбинации, для которых точное поведение не реализовано.
- Не игнорировать `minimum_should_match`; при неподдерживаемом значении возвращать `422`.
- Решить и протестировать поведение `bool` с единственным `should`, с `must` + `should`, пустыми массивами и вложенными bool.
- `filter` не входит в согласованный минимальный список. Не поддерживать его без отдельного решения.
- Неопределённые комбинации не трактовать «по догадке».

### 8.6 `wildcard`

Предусмотреть wildcard-поиск для совместимых шаблонов с преобразованием `*` в SQL `LIKE` `%` и `?` в `_`, если реализация и тесты обеспечивают корректную семантику.

```json
{"wildcard":{"message":"*error*"}}
```

Пример SQL:

```sql
message LIKE ?
```

Параметр:

```json
["%error%"]
```

Обязательные правила:
- Значение передавать только параметром.
- Экранировать символы SQL LIKE, имеющие специальный смысл (`%`, `_`, escape-символ), если они пришли как литералы из исходного шаблона.
- OpenSearch wildcard `*` и `?` преобразовывать осознанно; не считать их полной заменой всех возможностей SQL LIKE.
- Явно определить escape-семантику и покрыть её тестами.
- Не использовать regex `match` как незаметную замену wildcard.
- Если шаблон или опции не поддерживаются, вернуть `422`, не выдавать потенциально неверный SQL.
- Уточнить поведение wildcard по регистру и анализаторам OpenSearch; не обещать полную эквивалентность без согласования mapping.

## 9. Внутренняя архитектура

### 9.1 Основной конвейер

```text
HTTP JSON
   |
   v
Controller / DTO validation
   |
   v
Table & field validation
   |
   v
OpenSearchQueryParser
   |
   v
AST (QueryNode)
   |
   v
ClickHouseSqlGenerator
   |
   v
Translation result: SQL + ordered parameters
```

Обработка ошибок выполняется единым слоем `@RestControllerAdvice`.

### 9.2 Разделение ответственности

- **Controller:** HTTP, DTO, вызов сервиса, возврат ответа. Не содержит алгоритмов разбора DSL или генерации SQL.
- **Service:** координирует валидацию, парсинг и генерацию.
- **TableRegistry / SchemaProvider:** предоставляет разрешённые таблицы и поля из конфигурации.
- **OpenSearchQueryParser:** преобразует JSON-дерево в AST; не генерирует SQL.
- **AST:** типизированные узлы условий; не зависит от Jackson и SQL.
- **ClickHouseSqlGenerator:** преобразует AST в SQL и параметры; не разбирает исходный JSON.
- **Exception handler:** отображает типы доменных ошибок в HTTP-коды и ErrorResponse.
- **Configuration properties:** загружает YAML и валидирует конфигурацию при старте.

### 9.4 AST

AST должен представлять логический смысл запроса, а не повторять структуру JSON один-в-один. Использовать типизированные узлы и неизменяемые структуры, если это удобно выбранной версии Java.

Пример концептуального дерева:

```text
And
 ├── Comparison(source, EQ, "192.168.1.10")
 └── Not
     └── Comparison(message, EQ, "debug")
```

AST не должен содержать SQL-фрагменты, названия HTTP-кодов или Jackson `JsonNode`.

### 9.5 SQL и параметры

Генератор возвращает результат вида:

```java
record SqlBuildResult(String sql, List<Object> parameters) {}
```

SQL содержит placeholders, а параметры — значения в порядке их появления в SQL. Для каждого узла генератор должен добавлять placeholders и параметры согласованно.

Уточнение: `?` — выбранная демонстрационная форма placeholder. До будущего JDBC-выполнения проверить совместимость placeholder-стиля с используемым ClickHouse JDBC-драйвером/клиентом. Не утверждать, что любой ClickHouse-клиент принимает JDBC `?` без адаптера.

## 10. Обработка ошибок

Использовать единый формат ответа:

```json
{
  "error": "UNSUPPORTED_OPERATOR",
  "message": "Operator 'fuzzy' is not supported",
  "path": "query.bool.must[0].fuzzy"
}
```

Рекомендуемые HTTP-коды:

| HTTP | Категория | Пример |
|---|---|---|
| 400 | Некорректный JSON или структура собственного API | отсутствует `query`, неверный тип `table`, синтаксически повреждённый JSON |
| 422 | JSON корректен, но DSL-конструкция не поддерживается или не может быть корректно преобразована | `fuzzy`, неподдерживаемый параметр `range`, неподдерживаемая комбинация `bool` |
| 500 | Неожиданная внутренняя ошибка приложения | необработанное исключение |

Также определить отдельные error codes для неизвестной таблицы и поля. Рекомендуемое решение: неизвестная таблица/поле — `422` как корректно сформированный запрос с недопустимым контекстом, либо `400` как нарушение контракта API; выбрать единый вариант и закрепить тестами. Не раскрывать stack trace клиенту.

Путь `path` должен указывать на проблемный узел, когда он известен. Если определить путь невозможно, поле может быть `null` или отсутствовать.

## 11. Тестирование

### 11.1 MVP: unit-тесты без БД

Обязательные группы:
1. `term`: строковое и числовое значение.
2. `terms`: несколько значений, один элемент, пустой список.
3. `range`: каждая граница и комбинации границ, неверные типы.
4. `exists`: корректная форма, неизвестное поле.
5. `bool`: AND, OR, NOT, вложенность, пустые группы, ограничения `minimum_should_match`.
6. `wildcard`: `*`, `?`, литеральные `%` и `_`, escape-поведение.
7. Allowlist: неизвестная таблица и поле.
8. Ошибки: корректные коды, сообщения и JSON path.
9. Порядок параметров совпадает с порядком placeholders.
10. Защита от SQL injection: вредоносное значение остаётся параметром; вредоносное имя таблицы/поля отклоняется.

Тестировать не только текст SQL, но и список параметров. Для SQL допустимо нормализовать пробелы в тестовом helper, но не скрывать различия операторов и скобок.

### 11.2 Последующий этап: интеграционная проверка двух БД

Вне MVP, отдельным этапом:
- Запуск OpenSearch и ClickHouse локально через официальные Docker-образы.
- Создание тестового индекса и соответствующей таблицы.
- Генерация набора одинаковых логов с одинаковыми ID.
- Загрузка данных в обе системы.
- Выполнение исходного DSL в OpenSearch и сгенерированного SQL в ClickHouse.
- Сравнение множеств ID и анализ расхождений.
- Фиксация различий mapping, типов, анализаторов, NULL/missing и wildcard semantics.

Не требуется собирать OpenSearch или ClickHouse из исходников GitHub.

## 12. Нефункциональные требования

- Код компилируется и запускается локально по инструкции README.
- Проект собирается одной стандартной командой Maven/Gradle.
- Конфигурация таблиц не зашита в бизнес-логику парсера.
- Нет подключения к БД в MVP.
- Неподдерживаемые конструкции не игнорируются.
- Значения запроса не конкатенируются непосредственно в SQL.
- Компоненты парсинга и генерации можно тестировать независимо.
- Логи приложения не должны без необходимости содержать полные пользовательские запросы и чувствительные значения.
- Публичные классы и нетривиальные решения документируются кратко и по делу.

## 13. Критерии приёмки MVP

MVP считается готовым, если:
1. Приложение стартует локально.
2. Swagger UI доступен и позволяет отправить пример запроса.
3. `POST /api/v1/query/translate` принимает контракт `{table, query}`.
4. Корректный `term` преобразуется в SQL и параметр.
5. Реализованы и протестированы все операторы, заявленные как поддерживаемые в MVP, либо явно зафиксирован согласованный поднабор с причинами.
6. Неизвестная таблица/поле отклоняется.
7. Неподдерживаемый оператор возвращает `422` и полезный путь.
8. Ошибки JSON/контракта возвращают `400`.
9. Неожиданная ошибка возвращает безопасный `500`.
10. Unit-тесты проходят.
11. В README описаны запуск, endpoint, формат запроса, ограничения и запуск тестов.
12. В MVP отсутствуют подключения к OpenSearch и ClickHouse.

## 15. Открытые вопросы и допущения, требующие проверки

Эти пункты не следует выдавать за окончательно согласованные требования:

1. **Типы полей и схема:** отдельные колонки или JSON/Object; типы и Nullable-семантика.
2. **OpenSearch mapping:** `keyword`/`text`, анализаторы, нормализация и регистр.
3. **`bool.should`:** точная поддержка `minimum_should_match` и поведение при наличии `must`.
4. **`exists`:** эквивалентность отсутствующего ключа, NULL и пустого значения.
5. **`wildcard`:** escape-правила, регистр, `case_insensitive`, обработка `?`, wildcard только в начале/конце или в любой позиции.
6. **ClickHouse placeholder syntax:** проверить при выборе будущего драйвера/клиента.
7. **Табличные имена:** нужны ли database-qualified identifiers и фиксированная база.
8. **Unknown table/field status:** выбрать 400 или 422 и закрепить контракт.
9. **Лимиты:** максимальный размер JSON, глубина bool, число элементов `terms`, длина wildcard.
10. **Поддержка `filter`:** не включена в согласованный список MVP; добавить только отдельным решением.

## 16. Демонстрационный набор

### Пример 1 — term

Запрос:

```json
{
  "table": "windows_logs",
  "query": {
    "term": {
      "source": "192.168.1.10"
    }
  }
}
```

Ожидаемый результат:

```json
{
  "sql": "SELECT * FROM windows_logs WHERE source = ?",
  "parameters": ["192.168.1.10"]
}
```

### Пример 2 — bool

Запрос:

```json
{
  "table": "windows_logs",
  "query": {
    "bool": {
      "must": [
        {"term": {"source": "192.168.1.10"}},
        {"range": {"EventID": {"gte": 4000, "lte": 5000}}}
      ],
      "must_not": [
        {"term": {"message": "debug"}}
      ]
    }
  }
}
```

Ожидаемая логическая форма SQL (точные скобки и форматирование определяет генератор):

```sql
SELECT * FROM windows_logs
WHERE (source = ? AND EventID >= ? AND EventID <= ? AND NOT (message = ?))
```

Параметры:

```json
["192.168.1.10", 4000, 5000, "debug"]
```

### Пример 3 — wildcard

Запрос:

```json
{
  "table": "windows_logs",
  "query": {
    "wildcard": {
      "message": "*error*"
    }
  }
}
```

Ожидаемая форма:

```json
{
  "sql": "SELECT * FROM windows_logs WHERE message LIKE ?",
  "parameters": ["%error%"]
}
```

### Пример 4 — неподдерживаемый оператор

HTTP `422`:

```json
{
  "error": "UNSUPPORTED_OPERATOR",
  "message": "Operator 'fuzzy' is not supported",
  "path": "query.fuzzy"
}
```

---

**Итог:** MVP — самостоятельное Spring Boot MVC-приложение, принимающее `{table, query}` и возвращающее параметризованный ClickHouse SQL. Архитектурная основа — разделение валидации, OpenSearch DSL parser, AST и SQL generator. Реальное выполнение запросов и интеграционная проверка двух БД относятся к следующим этапам.

## 17. Согласованные решения к MVP 

Этот раздел фиксирует решения владельца проекта и уточняет предварительные варианты выше. При расхождении для реализации MVP приоритет имеет этот раздел.

1. **`bool`:** поддерживаются непустые массивы `must`, `filter`, `should`, `must_not`. `must` и `filter` формируют AND-группы; `should` всегда является обязательной OR-группой, в том числе вместе с `must` и `filter`; элементы `must_not` каждый отрицаются, результаты объединяются через AND. `minimum_should_match` не поддерживается и приводит к 422.
2. **Типы полей:** YAML задаёт тип каждого поля одним из `STRING`, `NUMBER`, `TIMESTAMP`, `BOOLEAN`.
3. **`exists`:** поддерживаются обычные колонки, перевод — `IS NOT NULL`; пустая строка считается существующим значением. Nullable, JSON, Map и отсутствующие ключи не входят в MVP.
4. **Timestamp:** `range` принимает только ISO 8601 с обязательным часовым поясом/смещением. Unix timestamp и другие форматы не поддерживаются.
5. **`range`:** разрешены `gt`, `gte`, `lt`, `lte`; пары `gt`+`gte` и `lt`+`lte` взаимоисключающие.
6. **`term` / `terms`:** только точное сравнение SQL `=` без анализа текста, токенизации и изменения регистра. `terms` требует непустой список до лимита, значения одного типа, соответствующего типу поля; смешанные типы и `null` запрещены.
7. **`wildcard`:** `*` и `?` преобразуются в `%` и `_`; литеральные `\`, `%`, `_` экранируются для SQL `LIKE`. Используется `LIKE ? ESCAPE '\\'`, шаблон передаётся параметром. `case_insensitive` не поддерживается. Регистр соответствует стандартному поведению выбранной ClickHouse-операции.
8. **Allowlist и HTTP-коды:** неизвестные таблицы и поля дают 422. Неизвестные операторы и свойства в DSL или верхнем уровне API также дают 422. Повреждённый JSON и некорректная форма обязательных полей контракта дают 400.
9. **Идентификаторы и placeholders:** разрешены только фиксированные простые имена таблиц/полей из YAML. Database-qualified и произвольные имена не поддерживаются. SQL использует `?`, а значения возвращаются отдельно в `parameters`; выбор будущего JDBC/client-драйвера отложен.
10. **Лимиты:** тело запроса — 1 MiB; вложенность DSL — максимум 10 уровней; `terms` — до 1000 значений; wildcard — до 1024 символов. Лимиты настраиваются в `application.yml`; превышение размера тела возвращает HTTP 413.
