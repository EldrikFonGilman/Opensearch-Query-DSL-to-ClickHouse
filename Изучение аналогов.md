# Исследование: OpenSearch Query DSL → ClickHouse SQL

Дата исследования: 11.11.2026.

## 1. Как устроены обе системы (то, что влияет на трансляцию)

| | OpenSearch | ClickHouse |
|---|---|---|
| Модель | JSON-документы в индексах, поверх Apache Lucene | Колоночная СУБД, таблицы MergeTree |
| Поиск | Инвертированный индекс; текст проходит через analyzer (токены, нижний регистр) | Разреженный первичный индекс по `ORDER BY`, партиции, skip-индексы (`tokenbf_v1`, `ngrambf_v1`, `bloom_filter`) |
| Релевантность | Есть скоринг (`_score`, `boost`) | Нет, только фильтрация и сортировка |
| Типы строк | `text` (анализируется) и `keyword` (точное значение) | `String`, `LowCardinality(String)`, регистр значим |
| Пропуски | Поле отсутствует = документ не попадает под `term`, но попадает под `must_not` | `NULL` в условии даёт `NULL`, строка отбрасывается (в том числе под `NOT`) |
| Вложенность | `host.name` — путь в JSON | Обычно плоская колонка (`host_name`) или `Map`/`JSON` |
| Язык запросов | Query DSL (JSON) | SQL |

Типичное хранение логов: в OpenSearch индексы по дням (`winlogbeat-2026.11.11`) с полями ECS
(`@timestamp`, `host.name`, `winlog.event_id`, `message`). В ClickHouse обычно одна широкая таблица
на источник (Windows, Linux/syslog, сетевые устройства) с `DateTime64` для времени, числовыми
колонками для ID событий и `String`/`LowCardinality` для остального. Имена колонок и типы заранее
неизвестны парсеру, поэтому он получает их из конфигурации (`translator.indices`).

Главные семантические разрывы, которые парсер обязан закрывать явно:
1. `match` по `text`-полю ищет токены без учёта регистра, а в ClickHouse `=` и `LIKE` регистрозависимы.
2. `NULL` и `must_not` ведут себя по-разному (см. ограничения в README).
3. Date math (`now-15m`) нужно превращать в выражение ClickHouse.
4. Скоринг не переносится, `_score` и `boost` игнорируются.

### Quesma подробнее

Из документации (docs.quesma.com/limitations): только чтение; ClickHouse и Hydrolix как целевые базы;
из Query DSL поддержаны boolean, match, match phrase, multi-match, query string, nested, match all,
exists, prefix, range, term, terms, wildcard; SQL, EQL, PPL и ES|QL не поддерживаются.

Почему не подходит как основа:
- **Это шлюз, а не библиотека.** Прокси между Kibana/OpenSearch Dashboards и базой, с коннекторами,
  ingest-пайплайном и собственной конфигурацией. Транслятор нельзя взять отдельно.
- **Язык Go.** Требование: Java + Spring Boot.
- **Лицензия Elastic License 2.0.** Это source-available, не свободная лицензия; копировать код в
  собственный компонент без юридической проверки нельзя.
- **Архив.** Репозиторий read-only, не развивается.
- **Избыточность.** Нам нужен «чистый» компонент без агрегаций и без прокси.

Ограничение исследования: я изучил README, документацию и страницу ограничений, но не клонировал
репозиторий и не читал исходный код парсера (в среде нет доступа к git).

## 3. Выбор подхода

**Решение: писать собственный парсер.**

- Нет open-source решения в нужном направлении, на Java и с пригодной лицензией.
- Задача ограничена (простой поиск, без агрегаций): набор из 12 типов запросов покрывает логи.
- Основная ценность — чистая архитектура и контролируемая семантика, а не широта охвата.

Что взято из найденного как идея: набор типов запросов Quesma задал приоритеты, а подход esql
(сравнение с эталонным API на реальной БД) указал на способ повышения доверия к результату в будущем
(см. «Дальнейшие шаги» в README).
